# Pitfall: UserPromptSubmit exit 2 bypasses the model + recursive-block via echoed trigger phrase

## Summary
A Claude Code hook that exits 2 on `UserPromptSubmit` **blocks the model from running entirely** — the assistant is not invoked. Stderr surfaces to the user in the UI ("UserPromptSubmit operation blocked by hook: ..."), not to the model. Compounding bug: if the stderr message echoes the original trigger phrase verbatim, subsequent prompts that paste or quote that message will re-trigger the block recursively.

## Context
Discovered live during v6.11.1 verification (2026-05-11). `hooks/workflow_enforcer.py` was upgraded to exit 2 when (a) prompt has Loop Mode trigger, (b) state file shows `check_shown=false`, (c) `strict_block=true`. The smoke tests passed. The live test in Claude Code revealed:

1. The block fires correctly. CC surfaces the stderr message to the user.
2. The model is never called. Stderr instructions addressed to "Claude" are dead text — Claude can't act on them because Claude doesn't run.
3. When the user re-sent the original prompt, CC apparently included the prior block message in the new prompt context. That message contained the phrase `loop trigger 'run until done' detected` — the substring `'run until done'` re-matched LOOP_TRIGGERS. Block fired again. And again on the third attempt. Three nested blocks visible in one screen.

## Details

**What stderr reaches**:
- ✅ The user, surfaced in the CC UI as a "blocked by hook" notice
- ❌ NOT the model — the assistant is not invoked at all on exit 2
- ❌ NOT the next turn's transcript — the blocked prompt never enters the conversation

**What this means for hook UX design**:
- Stderr "Action:" lines must address the **user**, not Claude. "Emit the WORKFLOW CHECK block" is meaningless guidance — Claude can't emit anything when it isn't running.
- Recovery options must be things the user can do: send a different prompt, edit a config file, edit a state file.

**Recursive-block trap**:
- If the block message contains the trigger phrase verbatim (e.g., `Reason: loop trigger 'run until done' detected`), pasting or re-sending that message will re-trigger the block.
- Mitigation: escape, redact, or omit the literal trigger phrase from stderr. Use a placeholder like `[loop trigger]` or just describe what was detected without quoting.
- Alternative mitigation: match the trigger phrase only against `data["prompt"]` (the actual user input), not against the full input string — but CC pastes the block message INTO the next prompt, so this only helps if the comparison is exact-substring rather than full-input contains.

**Real-world recovery options that work** (after a recursive block):
1. Send a non-trigger prompt. Model runs, response shows WORKFLOW CHECK, Stop hook writes `check_shown=true`, next trigger prompt passes.
2. Manually edit `.agent/.nav-workflow-state.json` to set `check_shown=true`.
3. Disable in config: `workflow_enforcer_hook.strict_block: false`.

## Recommended Approach

For any future `UserPromptSubmit` blocking hook:

1. **Stderr addresses the user, not the model.** Write recovery instructions assuming the model is dead.
2. **Never quote the trigger phrase verbatim in stderr.** Either omit, redact, or generalize ("a Loop Mode trigger phrase was detected").
3. **Document that the model never sees the block.** Hooks at this lifecycle event are pre-model — they're harness-level, not model-level. Stop expecting the model to act on blocks.
4. **Test the recursive case explicitly.** Send the literal stderr message back as a prompt and confirm it doesn't re-trigger.
5. **Provide at least one zero-config recovery path.** A user blocked by a hook should always have a way out that doesn't require editing a state file.
