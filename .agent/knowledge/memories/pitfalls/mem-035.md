# Pitfall: PreToolUse stdout and additionalContext are silent — exit 2 is the only behavior-affecting channel

## Summary
A Claude Code `PreToolUse` hook's stdout — both plain text AND the structured `hookSpecificOutput.additionalContext` JSON shape — produces **no visible output in the model's context**. Empirically verified in v6.12.0 live test: the read guard hook fired correctly on all 5 Read tool calls (counter advanced 0 → 5, side effect file written), but neither the count-3 warn nor the count-5 escalation messages appeared in Claude's visible context. The dual-channel emit strategy that worked for `SessionStart` is dead on `PreToolUse`.

## Context
Discovered during v6.12.0 verification (2026-05-11). v6.12.0 shipped `hooks/nav_read_guard.py` as a warn-only PreToolUse Read hook with a defensive dual-channel `_emit()` function that wrote both:

1. A structured JSON payload: `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "additionalContext": <message>}}`
2. The plain message text on a trailing line.

We assumed at least one of these would surface — the structured JSON shape is documented for SessionStart and works there. It does not work on PreToolUse.

Live verification procedure: cleared the counter, did 5 sequential Read calls to non-allowlisted `.agent/` files. After completion: counter file `.agent/.nav-read-counter.json` showed `turn_count: 5` (proving the hook fired and incremented correctly). My visible context contained zero `[nav-read-guard]` text. No system-reminder, no injected additionalContext, no surface of any kind.

## Details

**What works on PreToolUse**:
- Side-effect file writes (the counter advanced correctly — the hook ran)
- `exit 2` to refuse the tool call (proven to work in workflow_enforcer.py, same exit-code mechanism applies)
- stderr accompanying exit 2 surfaces to the user in the CC UI (same path as UserPromptSubmit block)

**What does NOT work on PreToolUse**:
- Plain stdout text — silently discarded
- `hookSpecificOutput.additionalContext` JSON — silently discarded (works on SessionStart, not PreToolUse)
- Informational warnings — they have no effect on model behavior because the model never sees them

**Implication for hook design**:
- Any PreToolUse hook intended to influence model behavior must use `exit 2`. Warn-only PreToolUse hooks are architecturally dead — they record state the model cannot perceive.
- The counter that a warn-only hook writes can still be useful: it can be read by OTHER hooks (e.g., SessionStart could surface "prior session had a bulk-load event"), or by Stop hooks for cleanup. But the warn-output itself is wasted code.
- For the read guard specifically, v6.12.1 switched to: stderr (not stdout) for warns, AND added `strict_block: true` (default) that exits 2 at the escalation threshold. The counter IS the state-file ground truth that mem-027's three-condition gate requires.

**Contrast with other lifecycle events**:
- `SessionStart`: `additionalContext` IS injected as system context. Documented and verified.
- `UserPromptSubmit`: exit 2 blocks; stderr surfaces to user. Same as PreToolUse for the block path.
- `PreToolUse`: exit 2 refuses tool; stderr-on-block surfaces. Stdout/additionalContext silent.
- `PostToolUse`: **unknown as of v6.12.1**. Probe in progress (`hooks/nav_commit_reminder.py` probe version). Update this memory with findings.
- `Stop`, `PreCompact`, `PostCompact`: side-effect-only; no model-visible output channel expected.

**Why the dead `_emit()` matters**: shipping defensive dual-channel code that asserts a behavior we've proven doesn't exist is actively misleading to the next engineer. v6.12.1 removes `_emit()` entirely and replaces with `_warn()` (stderr) + `_block()` (sentinel-wrapped stderr + exit 2).

## Recommended Approach

When designing a new `PreToolUse` hook:

1. **If the hook needs to change model behavior**: use `exit 2` (block) gated on the three-condition discipline (trigger, state-file confirmation, config opt-out). Stderr message addresses the USER, not Claude — Claude is invoked but the tool call is refused, so the user is the one who needs recovery instructions.
2. **If the hook is purely a side-effect** (counter, log, sync): use stderr for advisory warnings (visible to user in UI but not to model), exit 0. Do NOT use stdout or `hookSpecificOutput.additionalContext` — they are dead channels.
3. **Never assume a documented JSON shape works on an event it wasn't specifically documented for.** `additionalContext` works on SessionStart; do not generalize without testing.
4. **The counter pattern is reusable**: a side-effect hook writing state can satisfy mem-027's "state-file confirmation" for a separate blocking hook (or even for itself on a later invocation). v6.12.1 read guard demonstrates self-referential state-file gating.
