# Pitfall: plugin manifest hooks that depend on $CLAUDE_PLUGIN_DIR fail silently when the variable is unset

## Summary

Plugin manifest hook commands wrapped in `if [ -n "$CLAUDE_PLUGIN_DIR" ]; then ... fi` (the v6.14.0 defensive guard) exit 0 with no output when Claude Code does not bind that variable in the hook execution environment. Every hook becomes an invisible no-op. Projects that have a project-local `.claude/settings.json` with hardcoded `${CLAUDE_PROJECT_DIR}` hook entries silently mask the failure — the manifest hook does nothing, but the project-local hook fires. Projects relying solely on the plugin manifest get zero injection and zero error signal.

## Context

Discovered 2026-05-15 during a workshop-prep audit. The Navigator source repo (`~/Projects/startups/navigator`) showed SessionStart injection working — sentinel `<!-- nav-session-start-injected:v1 -->` present in every session. A second project (`~/Projects/Workshops/gitnation-companion`) had Navigator initialized, plugin loaded, same Claude Code version (v2.1.142), same plugin version (v6.15.0) — but `/context` showed `Messages: 13 tokens`, no injection at all.

Initial hypothesis was a stale session not picking up the recent plugin reload. Wrong — a fresh `claude --dangerously-skip-permissions` after `claude update` still showed zero injection.

Differential investigation found the smoking gun: the navigator source repo has a project-local `.claude/settings.json` with an explicit SessionStart hook entry using `${CLAUDE_PROJECT_DIR}/hooks/nav_session_start.py`. The companion repo has no `.claude/` directory at all. With only the plugin manifest as the hook source, and the v6.14.0 guard failing open when `$CLAUDE_PLUGIN_DIR` is unset, every hook silently no-opped.

The v6.14.0 guard was added for a real reason: `workflow_enforcer.py` runs on every `UserPromptSubmit`, and when `$CLAUDE_PLUGIN_DIR` was unset the command resolved to `python3 "/hooks/workflow_enforcer.py"` which python rejected with a non-zero exit, blocking every prompt including `/nav:init` (chicken-and-egg). The guard prevented that — but it converted the failure mode from "hard block" to "silent no-op," which is arguably worse because nobody notices.

## Details

**Failure modes by hook**:
- `SessionStart`: silent — no injection, no error. Indistinguishable from "Navigator not initialized."
- `PreCompact`, `PostCompact`: silent — markers not written, summaries not appended.
- `Stop`, `PostToolUse:*`: silent — state files not updated, profile/graph sync skipped.
- `UserPromptSubmit` (`workflow_enforcer`): silent — workflow-check enforcement disabled.
- `PreToolUse:Read` (`read_guard`): silent — bulk-read counter never advances.

**Why smoke tests didn't catch it**: the v6.14.0 author smoke-tested the script directly (`python3 hooks/X.py`), which bypasses the manifest's shell guard entirely. The shell guard's behavior under unset `$CLAUDE_PLUGIN_DIR` was never tested end-to-end — only the script body was tested. A `bash -c "$MANIFEST_COMMAND"` style test in an empty env would have surfaced the silent-fail immediately.

**Why the navigator source repo masked it**: that project's `.claude/settings.json` was carrying the hooks via the v6.13.0–v6.13.0 distribution channel (which v6.13.0 was supposed to deprecate but didn't fully remove in this repo). The plugin manifest hooks were always silently failing in the navigator source repo too — they were just redundant with the working project-local entries.

**Why `_resolve_plugin_dir()` in the script body didn't save us**: the multi-tier fallback (`os.environ.get("CLAUDE_PLUGIN_DIR")` → hardcoded marketplaces path → `Path(__file__).resolve().parent.parent`) is robust IF the script runs. The script doesn't run if the manifest shell guard short-circuits before invoking python.

## Recommended Approach

When writing plugin manifest hook commands:

1. **Never rely on a single env var that the harness may or may not bind**. If the harness fails to bind it, the failure mode must be loud (stderr error) or graceful (fallback path), but never silent.

2. **Use shell parameter expansion fallbacks** for path-style env vars:
   ```bash
   python3 "${CLAUDE_PLUGIN_DIR:-$HOME/.claude/plugins/marketplaces/<marketplace-name>}/hooks/X.py"
   ```
   The flat `marketplaces/<name>` directory is maintained by Claude Code for every plugin install and contains all hook scripts. It works as a universal fallback. Missing path → python errors loudly to stderr — never silent.

3. **End-to-end smoke test manifest commands, not script bodies.** Verify the actual shell-level invocation works under unset, empty-string, and bound variations:
   ```bash
   env -u CLAUDE_PLUGIN_DIR bash -c "$MANIFEST_COMMAND"
   CLAUDE_PLUGIN_DIR= bash -c "$MANIFEST_COMMAND"
   CLAUDE_PLUGIN_DIR=/some/path bash -c "$MANIFEST_COMMAND"
   ```

4. **Verify hooks fire in a project that has no project-local `.claude/settings.json`.** This is the canonical "no backstop" environment that exposes plugin manifest bugs. The navigator source repo is NOT this environment — it has its own project-local hook entries that mask manifest failures.

5. **Renames cascade widely.** When renaming a marketplace or plugin (jitd-marketplace → navigator-marketplace, in this case), audit every script and SKILL.md for hardcoded references — both `auto_updater.py` and `claude_updater.py` were renamed at the time, but three hook scripts and 8 SKILL.md doc references were missed and survived several releases before the silent-fail audit surfaced them.
