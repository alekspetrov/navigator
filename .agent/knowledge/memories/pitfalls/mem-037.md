# Pitfall: Stop hook stamping check_shown=false on non-task turns deadlocks the next loop-trigger prompt

## Summary
`hooks/nav_workflow_state.py` was over-eager: any assistant turn that didn't contain the literal "WORKFLOW CHECK" string was recorded as `check_shown=false`, including `AskUserQuestion`-only turns and pure-text replies (session-start summaries, short clarifiers). Then `hooks/workflow_enforcer.py` (UserPromptSubmit) refused the next prompt containing a Loop Mode trigger, leaving the user with only manual escape hatches. Fixed in v6.15.3 by tristating the field: `True` if CHECK present, `False` only when the prior turn used a codebase-mutating tool without showing CHECK, `None` ("n/a") otherwise.

## Context
Reproduced live in the gitnation-companion project, 2026-05-18:
1. Assistant asked a clarifying resume-or-review question via `AskUserQuestion`. No CHECK block — none was needed; no task was underway yet.
2. Stop hook fired. `WORKFLOW CHECK` not in the text. Wrote `check_shown=false`.
3. User declined to answer, then typed `"Run until done via loop mode"`.
4. `workflow_enforcer.py` matched the loop trigger + read `check_shown=false` + saw `strict_block=true` → exit 2.
5. The three recovery options surfaced via stderr (different prompt / edit state file / disable strict_block) are all manual and annoying mid-flow.

The user reported "this issue occurs time to time" — it had been recurring since v6.11.1 shipped the strict_block branch.

## Details

**Why the prior implementation was wrong**:
- The state writer treated *every* assistant turn as one that "should have" emitted the CHECK block. That's only true for turns that act on a task.
- Turns the model issues for legitimate non-task reasons (asking clarifiers via `AskUserQuestion`, rendering the session-start summary, replying with a one-line acknowledgement, simplifying after a completion signal) have no business showing CHECK. Marking them as violations was a false positive every time.
- Cooperating with another blocking hook (`workflow_enforcer`) amplified each false positive into a hard user-visible refusal. Two hooks each correct in isolation, broken in composition.

**The tristate fix** (v6.15.3):

| Prior turn signal | `check_shown` | Enforcer behavior on loop prompt |
| --- | --- | --- |
| Contained "WORKFLOW CHECK" | `True` | Soft-warn (exit 0) |
| Used a codebase-mutating tool, no CHECK shown | `False` | Block (exit 2) — unchanged |
| Used only `AskUserQuestion` / read-only tools / no tools | `None` | Soft-warn (exit 0) |

Task-action tools that flip the field to `False`: `Edit`, `Write`, `MultiEdit`, `NotebookEdit`, `Bash`, `Task`, `Agent`. All other tools are treated as conversation/research and don't poison the state.

The state writer now parses `tool_use` blocks out of the transcript JSONL alongside text. `workflow_enforcer.py` is unchanged — it already gated on `check_shown is False`, so `None` falls through to the soft-warn path cleanly. A `tools_used` array is recorded in the state file for debugging.

**Why this matters beyond the immediate fix**:
- The general lesson is that state-writing hooks should only emit signals when the prerequisite the signal claims to measure was actually present. "Did the assistant show CHECK?" is only a meaningful question if "should the assistant have shown CHECK?" is also true. Conditional emission, not unconditional binary.
- When two hooks cooperate (one writes state, one reads it to block), every false positive in the writer is a deadlock waiting to happen in the reader. The composition is only as forgiving as its strictest component.

**Empirical recovery from the deadlock** while the v6.15.2 code was still active in the wild: edit `.agent/.nav-workflow-state.json` and set `last_turn.check_shown` to any non-`false` value. The patched hook from v6.15.3 keeps it that way on its own.

## Recommended Approach

For any future Stop-hook signal that another hook will block on:

1. **Emit only when the precondition holds.** If the field claims "did the assistant do X when X was required," then write the field only when X was required. Otherwise write `null` / omit the key.
2. **Make the reader treat ambiguous state as non-blocking.** `workflow_enforcer.py` already does this (`check_shown is False`, not `not check_shown`). Future readers should follow the pattern: positive signal for "violation confirmed," not "violation not refuted."
3. **Probe with tool_use blocks, not just text.** A turn's tool-call shape carries more signal than its text — pure-text replies, question-only turns, and edit-laden turns are all distinguishable from the JSONL transcript without heuristics on text length.
4. **Test the composition, not just the components.** Each hook passed its smoke test in isolation. The deadlock only manifests when both run in sequence against a real turn shape. End-to-end smoke tests must include "turn N + prompt N+1" pairs that cover every state-file value the writer can produce.
5. **Audit cooperating-hook pairs whenever you add a new state field.** When `nav_workflow_state.py` gains a new field, check what reads it and what happens for each possible value (including the new value).
