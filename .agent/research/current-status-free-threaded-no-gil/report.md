# Free-threaded CPython as of September 2026: versions, single-thread cost, and NumPy/pandas/Django readiness

## Summary

Free-threaded CPython is officially supported but still opt-in. CPython 3.13 (October 2024) shipped the build as experimental; 3.14 (7 October 2025) promoted it to supported status under PEP 779, and the What's New declares the PEP 703 implementation finished [1][2]. CPython 3.15, due October 2026, adds one stable ABI that loads on both GIL and free-threaded interpreters plus further scalability work, and no release has been committed to making free-threading the default [3][4]. The single-threaded penalty fell from 20-40% in 3.13 to roughly 5-10% in 3.14; the 3.14 documentation puts the pyperformance average between about 1% (macOS aarch64) and 8% (x86-64 Linux) [3][5], while independent single-workload benchmarks range from about 6% to as much as 33% [4][10]. A separate, less advertised cost is memory: larger non-GC object headers, the mimalloc allocator, immortal interned strings, and deferred frees [5]. NumPy and pandas both appear on the community compatibility tracker with released support (versions 2.1.0 and 2.2.3 listed), while Django, being pure Python, is out of the tracker's scope by design; Django's own test suite was reported running under free-threading in July 2026 and a CPython core developer is upstreaming scaling fixes [6][7]. The strongest counter-position is that "supported" describes the interpreter, not the ecosystem: any extension module that has not opted in re-enables the GIL for the whole process, and one April 2026 survey still marked pandas as partially re-enabling it [4]. What remains open is whether that pandas re-enable comes from pandas itself or a dependency, what 3.15's overhead numbers will be, and when Django will declare a formal support level.

## Q1. Which CPython versions support the free-threaded build, and with what status

### 3.13: experimental (Phase I)

PEP 703 (status Final, resolved 24 October 2023, Python-Version 3.13) is the design document for the build, and the Steering Council's acceptance laid out three phases: experimental, supported-but-optional, and default [8][2]. The 3.13 HOWTO is titled "experimental support" and tells readers to expect bugs and a substantial single-threaded performance hit [9]. Distribution started with 3.13: the official macOS and Windows installers can optionally install free-threaded binaries, and source builds use the `--disable-gil` configure option [5]. Wouters' retrospective at PyCon US 2026 summarises 3.13 as slow, with thread-safety issues and scalability problems where adding threads could make things slower, "But it proved that it worked." [3]

### 3.14: supported, not default (Phase II)

PEP 779 (Final, resolved 16 June 2025) defined the criteria for leaving the experimental phase; the Steering Council accepted it with a non-exhaustive list of requirements to be addressed during Phase II [2]. The 3.14 What's New lists "PEP 779: Free-threaded Python is officially supported" among the release changes and states that the implementation described in PEP 703 "has been finished, including C API changes, and temporary workarounds in the interpreter were replaced with more permanent solutions" [1]. Supported does not mean default: the interpreter ships as a separate `python3.14t` binary that users must opt into [4]. Independent write-ups from the release week describe 3.14.0 as the first release with official support for PEP 779 / PEP 703 free threading [10].

Operationally, the 3.14 HOWTO documents how to tell which build you are on and whether the GIL is actually off: `sys.version` contains "free-threading build", `sys._is_gil_enabled()` reports the runtime state, and `sysconfig.get_config_var("Py_GIL_DISABLED")` is the recommended build-configuration check [5]. The GIL can be re-enabled on a free-threaded build with the `PYTHON_GIL` environment variable or `-X gil`, and it is re-enabled automatically, with a printed warning, when a C extension not marked as supporting free threading is imported [5]. Two behavioural defaults differ from the GIL build: `thread_inherit_context` and `context_aware_warnings` are both true on the free-threaded build and false on the default build [5][1]. Documented limitations include immortalization of code constants and `sys.intern()` strings, unsafe cross-thread access to `frame.f_locals`, and iterators that are not safe to share between threads [5].

### 3.15: due October 2026

Wouters said 3.15 "will have a single, stable ABI for both GIL and free-threaded versions of the interpreter", so extension authors can build once and load on either build, and that "a lot of scalability improvements for free threading" are coming in 3.15 [3]. The same ABI is referred to as abi3t elsewhere [4]. One concrete scalability example is visible in the Django thread: lock contention on a `set` lookup in `HttpHeaders.UNPREFIX_HEADERS` exists "In 3.14t (but not 3.15t)" [7]. The community tracker carries a footnote for one package that "is fully supported on Python 3.15t and above, on 3.14t it may crash at runtime exit", which shows 3.15t already being treated as a distinct support target [6].

### Phase III (free-threaded by default): unscheduled

No specific version has been committed to for making free-threading the default; the timeline depends on library adoption [4]. PEP 779 itself leaves the Phase III decision to a future PEP and expects it to revolve around community support, willingness, and demonstrated benefit [2]. Wouters, explicitly speaking without Steering Council authority, predicted the switch will land after 3.16 (October 2027) and before 3.20 (October 2031), with Linux distributors and companies like Meta likely flipping the default first, and the GIL build disappearing "next decade" [3].

## Q2. Single-threaded performance cost, per version

| Version | Reported single-threaded overhead | Who reports it |
|---|---|---|
| 3.13 | about 40% on the pyperformance suite (official 3.13 HOWTO); 20-40% (Wouters, PyCon US 2026); ~40% (blog) | [9] [3] [4] |
| 3.14 | "roughly 5-10%, depending on the platform and C compiler" (What's New); pyperformance average ~1% on macOS aarch64 to 8% on x86-64 Linux (HOWTO); around 10%, ~3% on macOS, against a 15% hard Phase II target (PEP 779 at acceptance); 0-10%, usually ~5% on Linux/GCC (Wouters); ~6% on a 4-core machine (blog); 9% Fibonacci (Grinberg); 33% Mandelbrot (Medium) | [1] [5] [2] [3] [4] [11] [10] |
| 3.15 | No single-threaded numbers in this corpus; scalability work announced | [3] |

The reason the number dropped is documented: the specializing adaptive interpreter (PEP 659) is enabled in free-threaded mode as of 3.14, "which along with many other optimizations greatly improves its performance", and the penalty "is now roughly 5-10%, depending on the platform and C compiler used" [1]. The 3.13 HOWTO had identified the disabled specializing interpreter as the largest single cause of its roughly 40% overhead and set a target of 10% or less on pyperformance for the following release [9]. The HOWTO's more granular figure is that on the pyperformance suite "the average overhead ranges from about 1% on macOS aarch64 to 8% on x86-64 Linux systems" [5]. Wouters' account matches and adds the compiler dimension: "On Linux using GCC, it's usually around 5%, though it can go up to 10%, particularly with older compilers", and he was "still personally shocked that we got to 0% slowdown" on Arm hardware [3]. The residual cost comes from the machinery that replaces the GIL: biased reference counting with a fast path for the owning thread and atomic operations for others, deferred and per-thread reference counting for selected object types, per-object critical sections, and lock-free lists and dicts backed by quiescent-state-based reclamation [5][3].

Microbenchmarks from the release week are not uniformly consistent with the official range. One Mandelbrot study on Astral's Clang-built 3.14.0 interpreters found the single-process, single-threaded script ran 33% longer on the free-threaded build and the multiprocessing variant 43% longer, while the threaded variant ran about 47.7% faster than the GIL-build baseline; the author recommends benchmarking your own workload before choosing a concurrency approach [10]. One 4-core test set (prime counting, SHA-256 hashing, pure-Python matrix multiply) reported about 6% single-thread overhead on 3.14t and up to 3.5x throughput with four threads, versus zero multi-thread gain on the GIL build [4]. Two other independent runs put numbers on the same question. A pure-Python Fibonacci and bubble-sort matrix across interpreter versions measured 3.14's free-threaded interpreter at 91% of the standard interpreter's speed on single-threaded Fibonacci, against roughly 3.1x faster on four-thread Fibonacci and about 2x on four-thread bubble sort; its author does not recommend the free-threaded build for code not directly slowed by the GIL and warns that such generic benchmarks are of limited use for profiling an interpreter [11]. The Mandelbrot study above is the third [10]. A November 2024 CodSpeed PageRank study of 3.13t attributed that release's slowdown to the specializing adaptive interpreter being disabled and called the build experimental and not yet ready for production use because of the overall slowdown [12].

The cost that the headline percentage hides is memory. PEP 779 put a number on it at acceptance time: free-threaded Python showed about 15-20% higher memory use (geometric mean, as measured by pyperformance), the PEP proposed 20% as the Phase II target, and its authors said higher memory use is realistically the price of efficient, safe free threading [2]. The 3.14 HOWTO states the free-threaded build "will typically use more memory compared to the default build": non-GC objects carry a larger header ("None uses 32 bytes on the free-threaded build vs 16 bytes for the default build" on AMD64), every interned string becomes immortal, all objects are allocated through mimalloc across four separate heaps instead of pymalloc, and QSBR plus deferred and per-thread reference counting delay when memory is actually freed; `gc.collect()` forces the deferred frees and `MIMALLOC_PURGE_DELAY=0` shortens the allocator's release delay at a performance cost [5].

Historical context explains why this number gates everything: Greg Stein's 1996 fine-grained-locking patch failed because the single-threaded loss was unacceptable, and Wouters framed the constraint as "We can't slow down the interpreter by 50% in order to make multiple threads executing at the same time that much faster" [3].

## Q3. Library compatibility: NumPy, pandas, Django

Two framing facts apply to all three. First, the community tracker only lists packages with extension modules or that needed code changes; "pure Python code works without changes by design, hence this page does not aim to track pure Python packages" [6]. Second, ecosystem coverage is measured in wheels: Wouters called free threading "already a success" with support from more than 50% of the top 360 binary wheels on PyPI, crediting Meta and Quansight for both the porting and the education effort [3].

The failure mode to test for is the GIL re-enable. Importing an extension that has not declared support re-enables the GIL for the whole process; the official docs and Wouters both say a warning is printed [5][3]. One blog claims the re-enable happens with "no warning or error message" [4]; the primary sources contradict that, though the practical advice from the same blog stands: check `sys._is_gil_enabled()` after your imports, and treat a `True` result as a dependency problem, not an interpreter problem [4]. A flag to always disable the GIL exists as a workaround, but Wouters called using it "playing with fire" and suggested it only for testing [3].

### NumPy

The tracker lists NumPy with 2.1.0 as the associated version [6]. NumPy's own manual (v2.5) has a Thread Safety page with a dedicated free-threaded Python section; it explains that many NumPy operations release the GIL so threads spending time in low-level code run in parallel, that the easiest gains come when each worker thread owns its arrays, that concurrent read/write of a shared array yields racy results at best and can crash the interpreter (for example resizing an array while another thread reads it), and that ndarray-level locking may be added in future but for now users should prefer read-only sharing or their own locks [13]. An April 2026 survey of the tracker and ft-checker.com reports NumPy 2.3+ shipping free-threaded wheels that do not re-enable the GIL, with the note "Improved in 2.3, still some edge cases" [4]. Verdict: NumPy is compatible, although its own v2.5 manual still describes free-threaded support (new in NumPy 2.1 with CPython 3.13) as experimental; correctness of shared mutable arrays is the user's responsibility, as it always was, and arrays with dtype=np.object_ carry a new class of data race because their Python-object elements are no longer protected by the GIL [13].

### pandas

The tracker lists pandas with 2.2.3 as the associated version [6]. The upstream tracking issue (pandas-dev/pandas#59057, opened 20 June 2024) is now closed; its plan was to set up free-threaded CI, audit the C extensions (the note records `pandas_datetime` as thread-safe and `pandas_parser` as not thread-safe but never used from multiple threads within pandas), and test the Cython extension modules [14]. The same issue records the C extension modules being marked with the Py_mod_gil slot (#59135), the Cython free-threading directive enabled globally (#59248), and green CI with Cython nightly [14]; since the automatic GIL re-enable is triggered by importing an extension not marked as supporting free threading [5], those markings weigh against pandas' own modules being the trigger for the partial re-enable reported in the April 2026 survey. The April 2026 survey lists pandas with free-threaded wheels but "Partial" for GIL re-enable, "Some operations re-enable GIL" [4]. That survey is secondary and does not say which operations or whether the trigger is a pandas dependency rather than pandas itself. Verdict: pandas imports and runs on the free-threaded build; whether a given workload actually runs without the GIL must be verified with `sys._is_gil_enabled()` after the specific code paths are exercised.

### Django

Django is pure Python, so it is not on the tracker and "works" in the trivial sense [6]; Wouters' caveat for pure-Python code is that nothing needs changing unless the code already has multi-threading bugs, which the free-threaded build makes more likely to surface [3]. The questions are thread safety of its internals and dependencies, and scaling. The DjangoCon US 2025 talk "Free Threaded Django" (10 September 2025) was scoped around exactly that: which Django internals and dependencies are thread-safe, how free threading affects database adapters such as psycopg, sync versus async Django, and servers (gunicorn, uvicorn, and granian, the last described as a newer option that provides free-threaded support) [15]. In March 2026 Sam Gross opened a Django forum thread offering patches after multithreaded Zulip benchmarks "uncovered a number of scaling issues"; his examples were contention on the class-level `Field.creation_counter` (temporary `Field` instances created per request invalidate CPython's attribute lookup cache), bounded `@lru_cache(maxsize=N)` decorators that bottleneck because strict LRU updates metadata on every hit, and the `HttpHeaders` set-lookup contention fixed in 3.15t; Trac ticket #36983 tracks it [7]. His general guidance to reviewers: watch `threading.Lock`, shared mutable data, `functools.lru_cache`, and `random.random()` (the global generator has an internal lock) [7]. On 14 July 2026 Carlton Gibson reported that "With the recent asgiref 3.12 release, and some tweaks to the tests, we can now run Django’s test suite under free-threading", that a "Free Threading : Beta" trove classifier had been suggested, and that the ticket sits at Someday/Maybe with a proposal to rescope it to "Support running under free threading" [7]. One contributor who tried the optimisations called them "super brittle" and asked for regression tests [7]. A practitioner FAQ answers "Can I use free-threading with Django/Flask?" with yes-with-caveats, noting that web frameworks rarely bottleneck on CPU-bound Python and that ASGI servers can benefit from mixed async plus thread workloads [4]. Verdict: Django runs, and as of July 2026 its test suite can be run under free-threading (after asgiref 3.12 and some test tweaks), with the reporter expecting more thread-related issues to surface; it has no formal support declaration and its per-request scaling on free-threaded builds is still being fixed [7].

### Cross-cutting: when not to use free threading

The 3.14 release also added `concurrent.futures.InterpreterPoolExecutor` (PEP 734), which gives isolated interpreters per worker with the efficiency of threads; the What's New notes that isolating an extension module overlaps heavily with free-threading support work [1]. For workloads that need worker isolation rather than shared memory, that executor or multiprocessing is the better fit [4]. Wouters' broader caution is that "Sharing objects between threads is still problematic for performance", which is why scalable containers such as the ft_utils package exist [3].

## Key findings

- (learning) CPython 3.13 shipped free threading as experimental; 3.14 made it officially supported under PEP 779, still as an opt-in separate build, and no version has been committed to making it the default [1][2][4]
- (learning) The 3.14 single-threaded penalty is roughly 5-10% by platform and compiler, with a pyperformance average of about 1% on macOS aarch64 and 8% on x86-64 Linux, down from 20-40% in 3.13 [1][5][3]; independent 3.14 microbenchmarks scatter more widely, from about 6% (prime counting, SHA-256) through 9% (Fibonacci) to 33% (Mandelbrot on Clang-built binaries) [4][11][10]
- (pitfall) Importing any C extension not marked free-threading-safe re-enables the GIL for the whole process (with a warning), so `sys._is_gil_enabled()` must be checked after imports, not assumed from the interpreter binary [5][4]
- (pitfall) The free-threaded build uses more memory: 32-byte non-GC object headers on AMD64, immortal interned strings, mimalloc with four heaps, and QSBR-deferred frees that `gc.collect()` can flush [5]
- (pattern) On free-threaded NumPy, give each worker thread its own arrays or share arrays read-only; mutating a shared array from two threads is racy and can crash the interpreter [13]
- (learning) The community tracker lists NumPy (2.1.0) and pandas (2.2.3) with free-threaded support, but an April 2026 survey still reports some pandas operations re-enabling the GIL [6][4]
- (learning) Django's test suite runs under free-threading since July 2026 (asgiref 3.12), but the project has no formal support classifier and its scaling ticket is Someday/Maybe [7]
- (pitfall) Django-style scaling bottlenecks under free threading: class-level counters mutated per request, bounded `lru_cache`, and `random.random()`'s global lock [7]
- (decision) CPython 3.15 will ship one stable ABI that loads on both GIL and free-threaded builds, removing the need for separate extension builds [3][4]
- (pattern) Use `InterpreterPoolExecutor` (PEP 734, 3.14) when workers need isolation; use free threading when they need shared memory [1][4]
- (learning) The default switch is predicted by a Steering Council member to land after 3.16 (October 2027) and before 3.20 (October 2031), with distributors likely flipping earlier [3]

## Open questions

- Does pandas itself re-enable the GIL on some operations, or does a dependency? The April 2026 survey does not say; the pandas release notes for 2.2.3 onward or the tracker's per-project issue link would settle it.
- The tracker's text extraction preserved project names and one version number per row but not the column headers, so "NumPy 2.1.0" and "pandas 2.2.3" are read here as the first-version-with-support column; the rendered page (or its Markdown source on GitHub) would confirm the mapping; for NumPy the manual's own "New in version 2.1" note already corroborates 2.1.0 as the first version with support [13]. psycopg appears on the tracker with no version attached.
- What is 3.15's single-threaded overhead and how much of the scaling work landed? The 3.15 What's New after the October 2026 release would settle both.
- Will Django adopt the "Free Threading : Beta" classifier and rescope ticket #36983 to "Support running under free threading"? The Trac ticket and the forum thread are the sources to watch.
- The Quansight one-year recap of free-threading adoption was rate-limited during fetching and is absent; it would give ecosystem-wide percentages beyond Wouters' "more than 50% of the top 360 wheels" figure.
- Python 3.14.5 reverted the default build's incremental GC to the 3.13 generational GC after production memory-pressure reports [1]; whether the free-threaded build's separate collector [3] was affected is not stated in the corpus.
